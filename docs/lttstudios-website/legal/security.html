Security

How we protect user data, our vulnerability disclosure policy, and how to reach the security team.

Effective: 2026-06-02 · Version 1.0

Architecture: zero-backend by design

The most important security property of LTTStudios VideoBot: there is no LTTStudios server holding user data. We cannot be breached at scale because there is nothing to breach. Each user's tokens, sheets, logs, and cached videos live only on their own Windows machine.

Encryption at rest

Tokens

  • Algorithm: AES-128-CBC + HMAC-SHA256 (Fernet specification, cryptography.io/fernet)
  • Key derivation: hashlib.sha256(machine_id + SALT).digest() (single-pass, deterministic per machine)
  • Key source: Windows Machine GUID (HKLM\Software\Microsoft\Cryptography → MachineGuid)
  • Implication: tokens copied between machines cannot be decrypted on the new machine
  • Files: data/tokens.enc (Facebook), data/tiktok_tokens.enc (TikTok)

OAuth state

CSRF state parameter is a cryptographically random 32-byte token (secrets.token_urlsafe(32)) generated per OAuth flow. Validated server-side in the callback handler.

TikTok OAuth relay (optional)

Cross-machine TikTok OAuth uses an HTTPS relay endpoint. Bot polls the relay with HMAC-SHA256 signed requests (hash_hmac('sha256', "$state|$ts", $secret)) with 300-second timestamp validity window to prevent replay.

Transport security

  • All API calls use HTTPS with TLS 1.2 or higher
  • Certificate validation enforced (no verify=False anywhere)
  • OAuth callbacks served over HTTPS (Let's Encrypt certificates)

What we DON'T store

  • ❌ User passwords (we use OAuth — never see your FB/TikTok password)
  • ❌ Caption content in audit logs (only post IDs and event types)
  • ❌ Video file content beyond temporary cache during upload
  • ❌ Email addresses of users you message
  • ❌ Friend lists or contact graphs
  • ❌ Analytics about your usage of the bot itself

Audit log integrity

The audit log (data/audit_log.jsonl) is append-only JSONL with timestamp + event + minimal metadata. Rotated at 10MB, max 5 backup files retained. No tamper detection — but the file is local to the user's machine, so the security boundary is the OS-level access control.

Dependency security

We minimize third-party dependencies. Current production deps (see requirements.txt):

  • customtkinter — GUI framework (modern Tk wrapper)
  • Pillow — image processing
  • google-api-python-client, google-auth-oauthlib, google-auth — Google APIs
  • requests — HTTP client
  • cryptography — Fernet encryption
  • qrcode[pil] — QR generation for TikTok OAuth
  • pytz, tzdata — timezone handling

No analytics SDKs, no error reporting services, no payment SDKs, no push notification SDKs. Each dep has been reviewed for license compatibility and active maintenance.

Vulnerability disclosure policy

Scope

In scope for responsible disclosure:

  • The LTTStudios VideoBot desktop application
  • The OAuth callback flow (lttstudios.com/auth/*)
  • The TikTok OAuth relay (lttstudios.com/api/oauth-relay/*)
  • The marketing website (lttstudios.com/*)

Out of scope:

  • Vulnerabilities in third-party services we depend on (Meta, TikTok, Google) — report those to the respective vendor
  • Social engineering of LTTStudios staff
  • Physical attacks against LTTStudios infrastructure (we don't have any)
  • Theoretical vulnerabilities without a demonstrated impact

Reporting process

  1. Email security@lttstudios.com with a clear description, reproduction steps, and impact assessment
  2. If the vulnerability is sensitive, request our PGP key in your first email and we'll provide one
  3. We acknowledge within 48 hours for critical issues, 7 days for lower severity
  4. We work toward a fix and coordinate disclosure timing with you
  5. Public disclosure: we credit researchers (with permission) in the changelog after the fix ships

Safe harbor

If you make a good-faith effort to comply with this policy, we will:

  • Not pursue legal action against you
  • Not report you to law enforcement
  • Work with you to understand and resolve the issue quickly

Known limitations / acknowledged risks

Machine GUID-based key derivation

We use Windows Machine GUID as input to PBKDF2 for token encryption. An attacker with admin access to the machine can read the GUID from registry and decrypt the token file. This is by design — we trust the machine boundary, not the user account boundary. For higher security, store tokens on a hardware security module (not currently supported).

No code signing yet

The .exe binary is not signed with an Authenticode certificate. Users see a SmartScreen warning on first run. We plan to add code signing in 2026 H2 when budget allows ($300+/year for EV cert).

Bot HTTPServer binds to 127.0.0.1 only

The OAuth callback receiver listens on 127.0.0.1:8765 (FB) and 127.0.0.1:8766 (TikTok). It only accepts loopback connections, not LAN/WAN. Browser extensions on the same machine could theoretically read the OAuth code — same risk as any OAuth flow that uses localhost callback.
